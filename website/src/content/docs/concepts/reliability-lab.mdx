Vulkan promises at-least-once delivery with no loss. The reliability lab
is how that promise would be checked: an hour of real producers and
consumers against a real Postgres, with consumers killed and the database
paused along the way, and one verdict at the end. Pass means every committed
message was delivered or dead-lettered and nothing else happened. This
page is the proposal for that lab, written so you can judge what "pass"
would actually prove.

## What exists today

Vulkan is tested at unit scale and at mechanism scale. `go test -race`
covers the packages. About twenty failure-injection labs each run one
mechanism for a few minutes under a real Postgres: reclaim of an expired
lease, dead-lettering after the retry budget, shutdown that truncates a
batch mid-commit, exclusive keys, partition drops. A compat lab runs the
previous release against the current schema at every release checkpoint.

What none of them do is run long, run everything at once, and account for
every single message. A reclaim lab proves a reclaim works. It does not
prove that after an hour of reclaims, kills, and load spikes the total
still adds up.

## Proposed: a ledger and a checker

The lab is mostly bookkeeping. Postgres is the thing under test, so the
lab keeps its own books in a second schema on the same instance and the
final report is a SQL join between the two.

```
   producers                                              consumer instances
   ┌──────────┐   produce                       claim      ┌──────────┐
   │ p-1  p-2 │ ─────────────▶  vulkan.*  ◀───────────── │ c-1  c-2 │
   └──────────┘                 message_log                │ c-3      │
        │                       delivery_log               └──────────┘
        │ every attempt:        exception_queue                  │
        │ key, outcome                                           │ every handler call:
        ▼                                                        ▼ message id, outcome
   ┌─────────────────────────────────────────────────────────────────────┐
   │ lab.*   produce_ledger        handler_ledger        run_phase       │
   └─────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼  after producers stop and consumers drain
                                  the checker: one SQL join, one verdict
```

Every produce writes two facts to the ledger: that it was attempted, and
what came back. What comes back is one of three things. Committed, with
the idempotency key. Rejected, with the VK code. Or unknown, because the
connection died after the commit was sent and before the reply arrived.
Most test suites never model that third outcome; Kafka's own verifier has
no bucket for it. The lab resolves it after the run by looking the key up
in the message log: if the row is there the produce is counted as
recovered, if not it is nothing. Only a committed produce can be lost.

Every handler invocation writes one row too: message id, consumer group,
attempt, and whether the handler succeeded, failed, or the process died
before it could say.

After the producers stop, the consumers drain until the last committed
message of every producer has a delivery outcome, and then the checker
runs. It sorts every produced message into a named bucket, and the
buckets must add up:

```
   produced  =  success  +  dead  +  compacted away  +  other schema version

   committed keys  ==  message_log rows           (nothing lost, nothing invented)
   every message   -> >= 1 delivery ending success or dead
   anything outside a named bucket                 -> FAIL
```

There is no acceptable "dropped" bucket. Every expected skip has a name,
and a message that lands in none of them fails the run.

Duplicates are counted and reported, never failed. A consumer instance
killed between the handler returning and the commit is redelivered after
the lease expires, so a second success row for the same message is the
contract working. The [message lifecycle](/concepts/lifecycle/) page has
the redelivery window; the lab shows the count and where in the run each
one happened.

## Proposed: a run reads like one file

Each run is described by a scenario file with three sections: what is
being tested, what happens over time, and what must be true at the end.
It is meant to be read cold in under a minute. The file is a description,
not a program. Each scenario is also plain Go in the lab, written by hand
to match, and the report prints the scenario back from that Go in this
same format, so a stale file shows up as a diff.

```
# steady load, a pause, a saturating spike, slow ramp back, one kill

[input]
topic       orders           DeliveryLogMode all
consumers   fraud-scoring    handler fail rate 0.02, 3 retries then dead
duration    60m

[shape]
warm:       steady 200/s 10m
quiet:      pause 1m
flood:      saturate 64 in flight 5m
cooldown:   ramp 2000/s -> 200/s 10m
hold:       steady 200/s 34m

at 0m       consumers 3
at 20m      consumers 0
at 22m      consumers 8
at 45m      kill consumer 2

[expect]
lost          0
undelivered   0
unbucketed    0
duplicates    report
reclaims      0 outside chaos windows
recovery      <= 2m after quiet, flood, and the kill
```

The producer phases run back to back. Consumer counts and chaos actions
land at times measured from the start. On a timeline the same run looks
like:

```
  0m            10m 11m    16m         26m                               60m
  ├─── warm ────┼─q─┼ flood ┼─ cooldown ─┼───────────── hold ──────────────┤
     200/s        0   64 in   2000 -> 200/s            200/s
                      flight

  consumers  3 ──────────────────────┐   ┌── 8 ──────────────x──────────────
                                  20m└─0─┘22m               45m  kill c-2
                                                                 a reclaim is
                                                                 expected here
                                                                 and nowhere else
```

Two phases are there on purpose. Consumers at zero for two minutes means
the backlog must grow and then drain with nothing lost. Eight consumers
on a topic that needs three means oversubscription, and the checker still
expects zero reclaims outside the kill.

## Proposed: what pass means

The report is the scenario file printed back with the actual value beside
every expectation:

```
[expect]
lost          0                   actual 0          PASS
undelivered   0                   actual 0          PASS
unbucketed    0                   actual 0          PASS
duplicates    report              actual 3          message_id 118402, 118403, 391115
reclaims      0 outside windows   actual 1 inside   PASS   (45m02s, c-2 range 118400..118463)
recovery      <= 2m               actual 41s, 1m12s, 58s    PASS

[faults]
consumers 0 at 20m    ran
kill consumer 2 at 45m    ran

verdict: PASS
```

The three duplicates are the messages consumer 2 had finished but not
committed when it was killed, redelivered after its lease expired. They
are listed, not failed. The one reclaim sits inside the kill window, so
it passes. The same reclaim at 30m would fail the run: with no chaos, a
reclaim means a consumer instance lost a lease it should have held.

A verdict has three values, not two. Pass, fail, and unknown. Unknown is
what a run reports when the fault it was meant to exercise never
happened: a one-minute dev run whose lease never expired, a kill that
landed on an idle instance, a checker that itself errored. This is the
rule the lab borrows most deliberately from the suites that have lasted:
a test that passes while checking nothing is worse than one that fails.

Under a quiet scenario, no chaos and a fail rate of zero, the checker
also expects zero reclaims and zero dead-lettered messages. A reclaim
with nothing pushing on the system is a finding on its own.

## Where it goes from here

The first version is deliberately small: one plain topic, one consumer
group, a handler fail rate, four load levels, and the scenario file. Each
later stage adds one axis and one named bucket:

1. Kills of consumers and producers mid-work, and pausing Postgres past
   the lease so every instance loses its lease at once.
2. A compacted topic with message keys, where "compacted away" becomes a
   real bucket and per-key order is checked.
3. Two schema versions live at once, so "other schema version" fills.
4. Routing bindings and fan-out, then schedules.
5. Metrics and alert assertions read from `__system` at the end.

The checker never changes shape through those stages. Each one adds a
bucket to the sum and a fault the run must prove it reached.
