---
title: 'Proposed: exporting retained measurements'
description: Proposed OTel producer behavior, source-read health, portable naming, and lifecycle ownership.
---

Vulkan would derive alerts from recorded measurement history and export
retained values through an OTel producer. Core owns alert timing and restart
behavior; integrations consume actionable `active` and `resolved` alerts
without maintaining pending timers or suppressing startup alerts themselves.
The [shared alert direction](/decisions/0686/) is agreed and has not shipped;
the [step 3 calculation contract](/decisions/0688/) is approved. Core runtime timing is proposed in
[history-based alerts](/concepts/alert-history/).

## What exists today

The claimed metrics collector records deployment measurements, with a default
30-second poll rate. Consumer instances record changed session counters;
applications choose when to produce custom measurements. The
[metrics API](/reference/metrics/) reads their latest retained values and
history from `__system.metrics`, with a 24-hour retention setting.
`Measurement.At` records when a value was observed.

The current `otelvulkan` adapter registers observable instruments and reads
retained measurements during collection. Callers using their own meter must
arrange discovery of new names. A source-read error can leave Vulkan metrics
missing from an HTTP 200 response.

The current [alerts](/reference/alerts/) machinery evaluates live conditions
and records active, repeated, and resolved alerts. It does not implement the
history-based pending calculation below.

## Proposed: export through an OTel producer

`otelvulkan.NewMetrics` would build an external SDK producer. Each
`Produce(ctx)` call would use core's existing retained-measurement read and
convert the result to OTel data. The reader owns collection cadence. New
metric names appear on the next collection without instrument registration,
a discovery loop, or a retained measurement cache.

```text
OTel reader requests collection
    -> producer reads latest retained measurements within its timeout
    -> validates metric families
    -> returns gauges, cumulative counters, and exporter health
    -> reader passes the data to its exporter
```

Gauges retain their values and attributes. Counters retain their cumulative
totals: reading a stored total of 120 twice still exports 120. The source
does not establish counter start times, so the adapter must not invent a
reset at exporter startup. This proposal adds no universal expiry or
per-series freshness companions; observation times remain available through
the core API.

The caller owns its provider and Postgres pool. The convenience Prometheus
exporter owns its private provider. Stop collection and finish outstanding
calls before closing the pool. The producer needs no start or stop loop.

Use a dedicated Vulkan reader and exporter for periodic export: the pinned
SDK skips export when collection returns an error. External producer data
also bypasses SDK instrument Views and normal aggregation, so callers
cannot rely on those to filter attributes or convert cumulative totals to
deltas. See the SDK's [periodic reader](https://github.com/open-telemetry/opentelemetry-go/blob/v1.44.0/sdk/metric/periodic_reader.go).

## Proposed: report reads and rejected measurements

Keep the upstream OTel Prometheus exporter and expose source-read success.
HTTP 200 alone would not establish that Postgres was read successfully.
The proposed health signals are collection-local gauges with no attributes:

| OTel name | Unit | Prometheus name |
| --- | --- | --- |
| `vulkan.otel.source.read_success` | none | `vulkan_otel_source_read_success` |
| `vulkan.otel.measurements.rejected` | `{measurement}` | `vulkan_otel_measurements_rejected` |

They describe this adapter's collection, never persisted core measurements.
The rejection value counts retained rows omitted, once each, not families or
a lifetime total. A rejected family omits all its rows.

| Source result | Producer result | Prometheus result |
| --- | --- | --- |
| Read succeeds | Supported measurements, read success 1, rejection count | HTTP 200 when conversion and serving succeed |
| Read succeeds but is empty | Read success 1, rejection count 0 | No retained measurement series; absence is not an observed zero |
| Read cannot complete | Read success 0 together with the collection error | Can return HTTP 200 with the failure signal; no retained measurements |

On read failure, omit the rejection count because nothing was inspected.
The SDK's [manual reader](https://github.com/open-telemetry/opentelemetry-go/blob/v1.44.0/sdk/metric/manual_reader.go)
preserves producer data alongside its error; periodic export instead reports
the error and skips that collection. Prometheus collection does not inherit
the HTTP request context, so the producer's own timeout bounds its reads.
An exporter-health signal is an established [Prometheus pattern](https://prometheus.io/docs/instrumenting/writing_exporters/#failed-scrapes).

Both entry points would enforce one portable export contract. Use upstream
`UnderscoreEscapingWithSuffixes` translation to check final metric and
attribute names. Reject conflicting kind or unit within a metric family,
ambiguous translated names or attribute keys, and custom names that enter
the reserved `vulkan_` or exporter-owned namespace. Healthy families still
export; a current-collection rejection count and diagnostic identify loss.
Report rejection through the warning diagnostic `measurements cannot be
exported`, naming the conflicting original names and reason, without payloads.
Partial rejection does not return a
collection error: periodic readers must still export the healthy families.
Reserve the two health names even against retained built-in measurements;
reserve upstream metadata names and `otel_scope_` attribute names as well.

For example, custom `billing.queue_depth` and `billing_queue_depth` both
translate to `billing_queue_depth`. Reject both families rather than choose
by row order. This also restricts OTLP-only callers, but keeps both entry
points consistent. It does not rewrite retained measurements or enforce
metadata immutability across time.

## Proposed: derive alerts from history

Core would calculate pending duration from consecutive recorded observations,
with no pending-state table or user-managed timer. Extend the existing alert
framework, starting with partition count, then compaction read cost and worker
liveness. Collector progress uses that same path afterward. Conditions stay
check-specific; shared policy decides pending, recovery, and repeats. The
[history proposal](/concepts/alert-history/) covers pseudocode, suggested timing,
diagnostic visibility, and restart/concurrency boundaries. Existing hourly
schedules need review alongside pending durations. This adds no custom alert
framework or backlog alert.

## Proposed: observe collector progress independently

The collector would record completion only after the whole pass succeeds.
An independent scheduled check records which completion it can see, including
explicit absent evidence. Use attribute-free gauges in `__system.metrics`,
with unit `s` and Unix-second values:

| Measurement | Value | Observation time |
| --- | --- | --- |
| `vulkan.metrics.collector.completed_timestamp` | Full-pass completion timestamp | When completion was recorded |
| `vulkan.metrics.collector.observed_completion_timestamp` | Last completion seen, or 0 for no retained completion | When the independent read happened |

Completion follows all reads and writes, including concurrent topic work;
partial passes and uncommitted completion writes cannot establish success.
Startup never refreshes it. Completion timestamps must be positive; 0 in the
observation series means absent evidence and is unhealthy, not a read error.
A read error records no sample. Historical completion age uses that sample's
own observation time; future completion timestamps are unusable.

Use Postgres observation times and `At.UnixMicro()` ranks for both series.
Late writes retain history without replacing newer heads. Replayed schedules
record actual reads, never backdated observations; write retries reuse the
same sample time and idempotency key. Collector age defaults to
max(2m, 3 live collector poll intervals), with an explicit positive override.

Neither OTel nor a separate user-run server owns these observations. The
[shared alert calculation](/concepts/alert-history/#proposed-calculate-state-in-the-shared-controller)
handles duration and recovery. If all checking machinery stops, Vulkan cannot
produce an outage report while it is stopped.

## Proposed: deployment boundary

Configure one logical export target per installation. Multiple adapter
replicas read the same deployment totals; summing those replicas duplicates
the measurement. Provider resource identity belongs to the caller and must
identify the installation; the adapter adds no replica coordination.

Implementation must verify empty sources, read errors, partial rejection,
new names, concurrent collections, cancellation, and shutdown against the
pinned SDK. Diagnostic codes are allocated with their declarations and
reference pages when implemented; this proposal does not reserve serials.
