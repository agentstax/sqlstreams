---
title: 'Proposed: alerts from measurement history'
description: Shared pending policy, retained evidence, restart gaps, and inspectable alert evaluation.
---

Vulkan would calculate pending duration in its existing alert framework.
The [implementation plan](/decisions/0689/) starts in the existing alert
recording path. History-based duration and the public snapshot read below
have not shipped; standalone evaluator types are not an implementation mandate.
[OTel export](/concepts/metrics-export/) remains independent.

## Proposed: one policy for the existing checks

Each check owns its condition. The shared alert controller evaluates duration
and decides active, resolved, and repeated alerts. Start with partition count.
Producer and consumer registration retain their immediate, log-only condition
warnings; they neither record observations nor produce alerts.

Add `Pending *AlertPendingConfig` to each built-in alert config:

| Field | Proposed default | Meaning |
| --- | --- | --- |
| `Duration` | `2m` | Required span of consecutive unhealthy samples |
| `MaximumGap` | `2m` | Largest sample gap; also the newest sample's freshness limit |
| `Disabled` | `false` | A fresh unhealthy sample may activate immediately |

Keep `ScheduleExpression`; propose `@every 1m` for all four checks. Nil or
sparse pending config resolves defaults. Durations must be positive after
defaulting, even when disabled. Zero duration means default, not immediate.
No inference from a cron expression: a custom schedule needs a gap allowance
that covers its actual observations. Overnight gaps earn no duration.

Keep condition thresholds: partition count defaults to half the live lock
ceiling; compaction read cost to 10,000 partitions; worker liveness checks for
any unclaimed worker on the topic. Collector `MaximumAge` defaults to
max(2m, 3 live collector poll intervals), with a positive explicit override.
The existing four-hour repeat default and its retention bound stay.

Resolve current policy from the existing registered schedule, once per
calculation. Queued schedule messages request a check; an old payload must
not reinstate old thresholds. Startup warnings keep their existing defaults.
[Prometheus separates conditions from pending duration](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/);
Vulkan would derive duration from retained observations rather than a timer.

## Proposed: retain the facts used by each condition

Use `__system.metrics` and its existing measurement producers. Proposed
names below are gauges; observation time comes from Postgres at the source
read. The series key includes `alert` and `topic_id`, keeping renamed or
recreated topics distinct and independently scheduled checks separate.

| Measurement | Unit | Value |
| --- | --- | --- |
| `vulkan.alert.observed_partitions` | `{partition}` | Actual partition count, including healthy counts |
| `vulkan.alert.observed_compaction` | none | 1 when materialized compaction heads exist, otherwise 0 |
| `vulkan.alert.observed_unclaimed_workers` | `{worker}` | Per-topic unclaimed-worker count, including 0 |

Partition count records one count from its existing controller. Reuse that
controller's source read and condition comparison for registration warnings;
do not add another SQL derivation. Resolve the live ceiling once and apply
the resulting threshold to the entire history.

Compaction read cost records count and applicability together, at the same
observation time, in one committed batch. Interpret only matching pairs from
that check; a missing half is unusable evidence. Applicability 0 is healthy.
Do not join a collector's latest compaction value to a differently timed count.
Timestamp equality alone cannot distinguish two concurrent batches with the
same time. Pair identity and tie selection remain a compaction adoption gate.

Worker liveness keeps independent `WorkerSnapshots` reads and topic-scoped
continuity. If worker A recovers while B becomes unclaimed, the topic can
remain unhealthy. **Open before worker adoption:** counts prove the condition
but cannot reconstruct today's named-worker alert details after a concurrent
observation. Do not quietly drop those details, substitute an unrelated live
read, or add a snapshot store. The evidence/message contract needs review.

Collector completion and independent observations retain their
[timestamp contract](/concepts/metrics-export/#proposed-observe-collector-progress-independently).
All new evidence uses `At.UnixMicro()` ranks. Existing metric ranks and public
`History(ctx, limit)` behavior stay unchanged. Read errors produce no sample;
write retries reuse the same idempotency key and timestamp. A new source read
is a new observation. Threshold changes reevaluate raw history.

## Proposed: calculate state in the shared controller

This is logical pseudocode, not a callable API. `condition` interprets each
sample using its own observation time and the one resolved policy:

```text
evaluate(history, evaluationTime, policy, condition):
    select the retained time window; order by At then message id
    for equal At, use the highest message id
    if newest is missing, unusable, or older than policy.MaximumGap:
        return insufficient_evidence
    if condition(newest) is healthy:
        return healthy
    if policy.Disabled:
        return active

    earliest = newest
    walk backward while each sample is usable and unhealthy:
        stop before any gap greater than policy.MaximumGap
        earliest = that sample
    span = newest.At - earliest.At
    return active if span >= policy.Duration else pending
```

An exact threshold crossing is unhealthy for partition count. Collector
completion exactly at its age limit is healthy; future completion is unusable.
An exact maximum gap is allowed. One old sample cannot activate by waiting.
Only fresh healthy evidence resolves; pending or insufficient evidence cannot.

For `orders` topic 41, threshold 100 and two-minute pending:

```text
10:00  message 7101: count 105 -> pending, span 0m
10:01  message 7102: count 108 -> pending, span 1m
10:02  message 7103: count 110 -> active,  span 2m
10:03  message 7104: count  95 -> resolved
```

If message 7102 instead records 95, the first sequence ends without an alert.
If Vulkan stops overnight, the next unhealthy observation begins a new span.
A retained active alert stays active until fresh healthy evidence resolves it.
Restarting only the evaluator preserves a qualifying span in retained history.

## Proposed: extend Record and expose the same calculation

The scheduled partition-count check becomes:

```text
read count through the existing partition-count controller
record raw measurement, even when healthy
call shared AlertController.Record for partition_count + topic 41

inside Record:
    begin transaction
        LockHead(alert name + owner)
        resolve current policy, read history and database time after locking
        evaluate history using the shared calculation
        healthy -> existing recovery classification
        active -> existing activation / reminder classification
        pending or insufficient_evidence -> produce nothing
        build any alert from the selected evidence and resolved policy
        ProduceInTx only when classification requires an alert
    commit
```

Evidence survives an alert-write failure. Refreshing history after locking
prevents an earlier candidate from overriding a competing check's result.
Pending cannot enter today's no-alert-means-healthy branch. Reminders require
sufficient active evidence and use database evaluation time. Ambiguous commit
retries reread head and evidence; external notification consumption can retry.

Propose `AlertHandle.Snapshot(ctx)` alongside existing `Latest` and `History`.
It performs the same calculation over retained evidence and current policy,
with no observation or alert writes and no live worker sampling. It returns
an `AlertEvaluationSnapshot`: `Status`, `EvaluatedAt`, `ObservedAt`,
`UnhealthySince`, `ObservedDuration`, resolved `PendingDuration`, `MaximumGap`,
`PendingDisabled`, and a reason for insufficient evidence. Absent times are zero; the status
and reason distinguish absence from healthy evidence. Observed duration is
an established sample span, never elapsed time since a remembered start.
For active alerts it is a lower bound within the retained window, not total
incident age. Disabled pending reports a zero span from the newest sample.

`Latest` and `History` remain recorded active/resolved alerts. Snapshot may
say healthy before a scheduled check records recovery, or insufficient while
Latest remains active. Missing history returns insufficient evidence; failed
reads return errors. No persisted evaluation-state mirror or status gauges.

## Proposed: bound the evidence read

For evaluation time `E`, duration `P`, and maximum gap/freshness `G`, read
`[E - P - 2G, E]`, inclusive. This includes a predecessor across the pending
boundary. Disabled pending needs only `[E - G, E]`. Read retained rows without
a fixed count limit; require retention strictly longer than that window or
disabled retention. Validate duration arithmetic before reading.

Use observation time for eligibility; ids only break ties, never establish
commit order. Unusable intermediate samples break a span. A late commit can
change the next result without rewriting a prior alert. Enforce the logical
window even before physical cleanup; decoding/read errors abort evaluation.

## Proposed: adoption and cost checkpoint

Existing hourly checks become sixty times as frequent under the suggested
schedule, and healthy checks now write evidence. At one-minute cadence, one
partition-count series produces 1,440 samples per topic per day before retries.
The metrics topic retains its 24-hour setting. These are workload counts,
not benchmark results.

Before adopting defaults, measure the real partition-count path with targeted
labs across topic/partition counts: query time, rows written, and full check
duration. Do not duplicate SQL in a benchmark or optimize around an unmeasured
cost. A run taking longer than the allowed gap cannot prove pending duration;
the snapshot exposes its limited coverage, and existing check-failure metrics
and worker diagnostics remain available.

Review partition count end to end before compaction read cost, worker liveness,
and collector progress. Compaction pair identity and worker details remain
design gates before those checks adopt the shared calculation.
