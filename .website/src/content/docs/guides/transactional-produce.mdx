import ThreadAside from '../../../components/thread-aside/thread-aside.svelte';

Use `ProduceFunc` to commit a business write and its message together.
Use `InTransaction` with `ProduceInTx` when one transaction must produce
to several topics. [Why Vulkan](/why-vulkan/#one-commit-for-the-business-write-and-message)
explains the failure window this removes.

The examples assume registered producers and application-owned `orders`
and invoice tables. Replace their fields with your application's schema.

## Choose the verb

| Transaction | Payload already exists | Payload comes from database work |
| --- | --- | --- |
| Vulkan opens it | `Produce` | `ProduceFunc` |
| Your `InTransaction` closure owns it | `ProduceInTx` | `ProduceFuncInTx` |

`ProduceBatch` writes several messages on one topic in one transaction,
returning results in argument order. [Producer](/reference/producer/)
lists each method's parameters and errors.

## Write and produce together

The closure you pass to `ProduceFunc` runs inside the message's own
transaction. Run your business writes on the `tx` it hands you and
return the payload; both commit together, or neither does.

```go
func CreateOrder(ctx context.Context, instance *vulkan.ProducerInstance[OrderCreated], order Order) error {
	_, err := instance.ProduceFunc(ctx,
		func(ctx context.Context, tx vulkan.Tx) (*OrderCreated, error) {
			if _, err := tx.Exec(ctx,
				`INSERT INTO orders (id, total) VALUES ($1, $2)`, order.Id, order.Total); err != nil {
				return nil, err
			}
			return &OrderCreated{OrderId: order.Id}, nil
		}, nil)
	return err
}
```

Returning an error from the closure rolls back its statements and the
message. A commit error can still leave the caller uncertain whether the
transaction landed; it does not split the business write from the message.
[Side Effects & Retries](/guides/side-effects-and-retries/#retries-are-yours-to-own)
explains safe retries after an ambiguous result.

Three details about the closure:

- `tx vulkan.Tx` runs `Exec`, `Query`, `QueryRow`, `SendBatch`, and
  `CopyFrom` — the statement surface of a pgx transaction. For anything
  beyond that, `tx.Raw()` returns the underlying `pgx.Tx` (an escape
  hatch, not the default path).
- The payload comes back from the closure, not from a captured
  variable — so it can be built from what your own statements returned
  (a generated id, a computed total).
- Nothing hands you an idempotency key. A produce mints its own unless
  you set `ProduceOptions.IdempotencyKey`, and retrying across a crash
  means setting it — more in
  [Side Effects & Retries](/guides/side-effects-and-retries/).

Consumers cannot observe the message before its transaction commits.

## Prove it to yourself

1. Choose an unused order id, such as `order-9`, and **force a rollback**
   after inserting it:

   ```go
   _, err := instance.ProduceFunc(ctx,
   	func(ctx context.Context, tx vulkan.Tx) (*OrderCreated, error) {
   		if _, err := tx.Exec(ctx, `INSERT INTO orders (id) VALUES ($1)`, "order-9"); err != nil {
   			return nil, err
   		}
   		return nil, errors.New("rollback on purpose")
   	}, nil)
   ```

2. Check for that order and its message; neither should exist. Resolve the topic's id
   from the catalog once (each topic owns its physical tables, named by
   that id; say it returned `1`):

   ```sql
   SELECT id FROM vulkan.topic_config WHERE name = 'orders.created';

   SELECT count(*) FROM orders WHERE id = 'order-9'; -- 0
   SELECT count(*) FROM vulkan.message_log_1
   WHERE payload ->> 'order_id' = 'order-9'; -- 0
   ```

3. Replace the final return with `return &OrderCreated{OrderId: "order-9"}, nil`
   and run it again. Check `err` before proceeding. Both counts should now
   be `1`, provided `OrderCreated.OrderId` uses the JSON tag `order_id`.
   While the transaction is open, consumers cannot see its message.

## Several topics, one commit

To produce to more than one topic atomically, `client.InTransaction`
opens one transaction and hands your closure a `Tx` that every
instance's `ProduceInTx` accepts. One statement per topic:

```go
err := client.InTransaction(ctx, func(ctx context.Context, tx vulkan.Tx) error {
	if _, err := tx.Exec(ctx, `UPDATE orders SET status = 'paid' WHERE id = $1`, orderId); err != nil {
		return err
	}

	// produce last -- see the lock note below
	if _, err := invoices.ProduceInTx(ctx, tx, &InvoicePaid{OrderId: orderId}, nil); err != nil {
		return err
	}
	_, err := receipts.ProduceInTx(ctx, tx, &ReceiptRequested{OrderId: orderId}, nil)
	return err
})
```

<ThreadAside label="CAUTION" title="Do your own statements first; produce last">
Producing holds every consumer group on the topic at your message until
you commit. A claim only advances to the oldest uncommitted message id,
so an open transaction with a produce in it is a wall for the whole
topic, and every statement you run *after* the produce is time the wall
stands. Nothing in the types enforces the order, and nothing logs the
stall today -- consumers just lag.

For one topic, `ProduceFunc` makes the order structural: the closure
runs first and the produce is the last thing in the transaction by
construction. Reach for `InTransaction` plus `ProduceInTx` when you
need several topics in one commit, and put the produces at the end.

</ThreadAside>

Producing several **compacted** keys in one transaction adds a second
ordering rule. Each key's `compaction_head` row stays locked until you
commit, so two transactions taking the same keys in opposite order
deadlock: Postgres kills one of them (`40P01`) and rolls its whole
transaction back. `InTransaction` never reruns your closure, so that
retry is yours to write. Producing in message-key order avoids the
cycle, and `ProduceBatch` sorts its items the same way, so a consistent
order composes across both.

Two things stay yours after the commit guarantee — side effects the
transaction can't undo, and rerunning the closure when the outcome
was ambiguous. Both have their own page:
[Side Effects & Retries](/guides/side-effects-and-retries/).

<ThreadAside label="NOTE" title="Need to reach external systems too?">
If some messages must also flow to systems outside Postgres (another
org's Kafka, a partner webhook), your Vulkan topic already *is* a
transactional outbox — add a relay consumer group that forwards
downstream, with retries and
[dead-lettered messages](/guides/dead-letters/) for the flaky
remote end. The downstream operation still needs idempotency because a relay
can repeat after a crash.

</ThreadAside>

## Build a payload inside a shared transaction

Inside `InTransaction` you already hold `tx`, so `ProduceInTx` usually
suffices. Use `ProduceFuncInTx` when an existing producer function owns
the write and constructs the payload from its result:

```go
err := client.InTransaction(ctx, func(ctx context.Context, tx vulkan.Tx) error {
	_, err := invoices.ProduceFuncInTx(ctx, tx,
		func(ctx context.Context, tx vulkan.Tx) (*InvoicePaid, error) {
			var invoiceId int64
			if err := tx.QueryRow(ctx,
				`INSERT INTO invoices (order_id) VALUES ($1) RETURNING id`, orderId).Scan(&invoiceId); err != nil {
				return nil, err
			}
			return &InvoicePaid{OrderId: orderId, InvoiceId: invoiceId}, nil
		}, nil)
	return err
})
```
