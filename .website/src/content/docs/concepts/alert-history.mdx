---
title: 'Alerts from measurement history'
description: Shared pending policy, retained evidence, restart gaps, and read-only evaluation diagnostics.
---

The three topic alerts calculate pending duration from collector-owned
measurements. Each condition interprets its samples; one shared calculation
applies duration, freshness, and gap rules. Every worker keeps
`Evaluate -> Record`. Alerts do not produce their own evidence.

## One policy for all three checks

`PartitionCountAlertConfig`, `CompactionReadCostAlertConfig`, and
`WorkerLivenessAlertConfig` expose the same direct fields:

| Field | Default | Meaning |
| --- | --- | --- |
| `ScheduleExpression` | `@every 1m` | How often the scheduled check evaluates retained evidence |
| `PendingDuration` | `2m` | Required consecutive unhealthy sample span |
| `MaximumGap` | `2m` | Largest sample gap and newest-sample age |
| `DisablePending` | `false` | Permit immediate activation from fresh unhealthy evidence |

Zero-valued timing fields resolve defaults; resolved durations must be positive,
even when disabled.
Unchanged alerts repeat every four hours. The collector's default interval
is 30 seconds, independent of the one-minute check interval.

For example, `orders` first has an unhealthy sample at 10:00. Checks at
10:00:20 and 10:01:20 remain pending; a check at 10:02:20 can activate using
the samples through 10:02. This assumes collection and check execution keep
up; the schedule interval is not a delivery-time guarantee.

Scheduled checks use the consumed message's payload. Changing a declaration
affects subsequently produced messages; queued checks retain their settings.
Payloads without pending fields resolve the defaults. Registration warnings
use the same condition with pending disabled, require fresh evidence, and
remain log-only.

## Collector-owned evidence

The metrics package owns collection and storage in `__system.metrics`.
`Measurement.Metadata` carries JSON facts from the same observation as its
number. Metadata is returned by retained reads and metrics consumers, but
does not participate in the message key or become OTel labels.

| Measurement | Value | Metadata |
| --- | --- | --- |
| `vulkan.topic.state.partitions` | Message-log partition count | `compaction_status`: `compacted` or `uncompacted` |
| `vulkan.topic.workers.unclaimed` | Unclaimed workers owned by the topic and its consumer groups | `workers`: name, owner, and target instances |

Partition count and compaction status come from one TopicSnapshot. Compaction
read cost reads that one measurement, not two independently retained series.
The existing compacted gauge remains available to metric consumers.

Worker count and identities come from one WorkerSnapshots read. A healthy
collection produces zero with an empty list. Failed reads produce no sample.
Only fields needed for the alert are retained, not worker configuration
documents.

Partition count defaults to half the live lock ceiling, resolved once per
evaluation. Compaction read cost defaults to 10,000 partitions and applies
only to compacted topics. Worker liveness is unhealthy when any owned worker
is unclaimed. A change in which worker is unclaimed does not reset the
topic-level condition; the newest sample supplies the alert's names.

Series retain the existing topic-name identity: rename changes the series
key; a recreated topic with the same name shares it. Missing required metadata
is insufficient evidence. Older partition samples remain usable for partition
count but cannot establish compaction health. Decode and read errors abort
evaluation.

## Calculate pending duration

This is logical pseudocode, not a callable API:

```text
each condition interprets its retained samples as healthy, active, or insufficient

shared calculation:
    read newest first, ordered by CreatedAt then message id
    for equal CreatedAt, use the highest message id
    if newest is missing, unusable, or older than MaximumGap:
        return insufficient
    if newest is healthy:
        return healthy
    if pending is disabled:
        return active

    walk backward through consecutive unhealthy samples
    stop at healthy/unusable evidence or a gap larger than MaximumGap
    span = newest.CreatedAt - earliest.CreatedAt
    return active if span >= PendingDuration else pending
```

An exact threshold crossing is unhealthy. An exact maximum gap is allowed.
One sample cannot become active by waiting. Overnight gaps earn no duration;
restarting only the evaluator preserves a qualifying span in retained history.

For `orders`, topic 41, threshold 100 and two-minute pending:

```text
10:00  message 7101: count 105 -> pending, span 0m
10:01  message 7102: count 108 -> pending, span 1m
10:02  message 7103: count 110 -> active,  span 2m
10:03  message 7104: count  95 -> healthy
```

If message 7102 instead records 95, the first unhealthy span ends without an
alert. If Vulkan stops overnight, the next unhealthy observation starts a new
span. A retained active alert stays active until fresh healthy evidence resolves it.

## Recording and evidence gaps

`AlertEvaluationSnapshot` carries `State` and `Finding`. Finding is present
for pending and active conditions. Evaluation states are not additional
statuses produced to the alerts topic.

```text
result = condition.Evaluate(topic, consumed policy)
AlertController.Record(alert name, topic, result)

inside Record:
    pending or insufficient -> leave recorded alert unchanged
    healthy or active:
        begin transaction
        LockHead(alert name + owner)
        classify recovery, activation, or repeat
        ProduceInTx only when classification requires an alert
        commit
        log committed transitions
```

Insufficient evidence increments the existing failed-topic check count.
Registration warnings log insufficient evidence. Pending is not a failed
check. Reminders require sufficient active evidence; an evidence gap cannot
repeat or resolve an alert.

The head lock serializes alert transitions, not evidence reads made before
Record. Metrics collection is independent of alert-write success. Consumers
of the alerts topic still follow normal delivery and retry behavior.

## Bound the evidence read

For evaluation time `E`, duration `P`, and maximum gap `G`, read
`[E - P - 2G, E]`, inclusive. This includes a predecessor across the pending
boundary. Disabled pending needs only `[E - G, E]`. Read retained rows without
a fixed count limit; require retention strictly longer than the window or
disabled retention. Validate duration arithmetic before reading.

Evaluation uses database time. Evidence uses stored `CreatedAt`; message ids
break timestamp ties. A delayed write can count as fresh evidence, an accepted
tradeoff [0690](/decisions/0690/). `Measurement.At` remains observation metadata,
not the pending clock. History remains bounded even before physical cleanup.

## Inspect the current evaluation

`AlertHandle.Snapshot(ctx)` answers: what does the retained evidence
say now, under the current declared policy? It supports all four built-in
alerts and returns `(*AlertEvaluationSnapshot, error)`, without producing
measurements, recording alerts, or changing a consumer cursor.

The return shape uses evaluation `State`, keeping it distinct
from a recorded alert's active/resolved status:

| Field | Meaning |
| --- | --- |
| `State` | Healthy, pending, active, or insufficient evidence |
| `Finding` | The existing condition finding for pending/active; absent otherwise |
| `EvaluatedAt` | Database time used by this evaluation |
| `ObservedAt` | Newest sample's stored time; collector progress uses its completion timestamp; zero when unavailable |
| `UnhealthySince` | Start of the established unhealthy span, bounded by the evidence window |
| `ObservedDuration` | Unhealthy duration established by this evaluation |
| `PendingDuration`, `DisablePending` | Resolved pending settings used |
| `MaximumGap` | Resolved sample-gap limit for topic alerts; zero for collector progress |
| `MaximumAge` | Resolved completion-age limit for collector progress; zero for topic alerts |
| `Reason` | Human-readable explanation for insufficient evidence; empty otherwise |

Healthy and insufficient results report zero unhealthy start/duration.
With pending disabled, topic alerts skip the history scan and report zero
span; collector progress still calculates its coverage-backed overdue span.
An active span is bounded evidence, not the condition's lifetime. Reason text
is for display; callers branch on State.

The call follows the existing ownership and evaluation paths:

```text
AlertHandle.Snapshot(ctx):
    resolve the owner and built-in alert
    read its current schedule payload through the schedule controller
    decode and resolve that policy
    run the same condition.Evaluate used by scheduled checks
    return the evaluation with its timing and evidence reason
```

The evaluator retains diagnostic facts as it makes each decision.
Snapshot exposes those facts without repeating the calculation.
Scheduled workers call Evaluate with the consumed payload,
then Record. Snapshot never consumes a scheduled message.

For example, `orders`, topic 41, has unhealthy messages 7101 and 7102 one
minute apart. A current two-minute pending policy gives Snapshot `pending`
with `ObservedDuration: 1m`. A queued check carrying the earlier one-minute
policy can still activate. Snapshot explains the current declaration, not
the last check or the next queued check.

Missing schedules, unsupported alert names/scopes, malformed policy, and
database/decode failures return errors; no default policy is substituted.
Missing, stale, or unusable evidence returns an insufficient snapshot with
its reason. Suspended schedules remain inspectable: Snapshot evaluates the
condition, not whether automatic checks are running.

`Latest` and `History` remain recorded active/resolved messages. Snapshot
could say insufficient while Latest stays active, or healthy before a
scheduled check records recovery. The snapshot is not persisted.

Collector progress uses manager lease history independently of completion
measurements; see [collector progress](/concepts/metrics-export/#observe-collector-progress-independently).

The [cadence cost checkpoint](https://github.com/agentstax/vulkan/blob/main/.bench/alertcadence/RESULTS.md)
measures the existing reads and recording path on Postgres 18. One-minute
checks increase both history reads and alert-head updates, including for
unchanged conditions. Larger installations can supply a longer
`ScheduleExpression` without changing collection. The metrics topic retains
its 24-hour setting.

Existing declarations change when `System().Register` is called with the new
defaults. Explicit schedule expressions remain explicit; registration preserves
suspension. The schedule returned by
`client.Scheduler("alert.partition_count").Get(ctx)` exposes the stored cadence
in `Expression`; use the corresponding schedule name for the other checks.
