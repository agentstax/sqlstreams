---
title: 'Exporting retained measurements'
description: OTel producer behavior, source-read health, portable naming, and lifecycle ownership.
---

SQLStreams derives alerts from recorded measurement history and exports
retained values through an OTel producer. Core owns alert timing and restart
behavior; integrations consume actionable `active` and `resolved` alerts
without maintaining pending timers or suppressing startup alerts themselves.
Core timing and read-only diagnostics are described in
[history-based alerts](/concepts/alert-history/).

## What exists today

The claimed metrics collector records deployment measurements, with a default
30-second poll rate. Consumer instances record changed session counters;
applications choose when to produce custom measurements. The
[metrics API](/reference/metrics/) reads their latest retained values and
history from `__system.metrics`, with a 24-hour retention setting.
`Measurement.At` records when a value was observed.

## Export through an OTel producer

`otel.NewMetrics` builds an external SDK producer. Each
`Produce(ctx)` call uses core's retained-measurement read and
converts the result to OTel data. The reader owns collection cadence. New
metric names appear on the next collection without instrument registration,
a discovery loop, or a retained measurement cache.

```text
OTel reader requests collection
    -> producer reads latest retained measurements within its timeout
    -> validates families and converts supported values
    -> adds source-read health and the current rejection count
    -> reader passes the data to its exporter
```

Attach it with `sdkmetric.NewManualReader(sdkmetric.WithProducer(measurements))`
and register that reader on the caller's provider. `NewExporter` attaches the
same producer to its private Prometheus reader. No instrument discovery is
required, and collections share no retained state.

Gauges retain their values and attributes. Counters retain their cumulative
totals: reading a stored total of 120 twice still exports 120. The source
does not establish counter start times, so the adapter must not invent a
reset at exporter startup. The producer adds no universal expiry or
per-series freshness companions; observation times remain available through
the core API.

External producer data bypasses SDK instrument Views and normal aggregation, so callers
cannot rely on those to filter attributes or convert cumulative totals to
deltas. See the SDK's [periodic reader](https://github.com/open-telemetry/opentelemetry-go/blob/v1.44.0/sdk/metric/periodic_reader.go).

## Report reads and rejected measurements

The upstream OTel Prometheus exporter exposes source-read success.
HTTP 200 alone does not establish that Postgres was read successfully.
The health signals are collection-local gauges with no attributes. Their catalog
scope is `exporter`; they have no stored `Latest` or `History` values:

| OTel name | Unit | Prometheus name |
| --- | --- | --- |
| `sqlstreams.otel.source.read_success` | none | `sqlstreams_otel_source_read_success` |
| `sqlstreams.otel.measurements.rejected` | `{measurement}` | `sqlstreams_otel_measurements_rejected` |

They describe this adapter's collection, never persisted core measurements.
The rejection value counts retained rows omitted, once each, not families or
a lifetime total. A rejected family omits all its rows.

| Source result | Producer result | Prometheus result |
| --- | --- | --- |
| Read succeeds | Supported measurements, read success 1, rejection count | HTTP 200 when conversion and serving succeed |
| Read succeeds but is empty | Read success 1, rejection count 0 | No retained measurement series; absence is not an observed zero |
| Read cannot complete | Read success 0 together with the collection error | Can return HTTP 200 with the failure signal; no retained measurements |

On read failure, omit the rejection count because nothing was inspected.
The SDK's [manual reader](https://github.com/open-telemetry/opentelemetry-go/blob/v1.44.0/sdk/metric/manual_reader.go)
preserves producer data alongside its error when it reaches the producer.
An already-canceled reader call stops before SQLStreams runs and supplies no health
gauge. Periodic export instead reports the error and skips that collection.
Prometheus collection does not inherit
the HTTP request context, so the producer's own timeout bounds its reads.
An exporter-health signal is an established [Prometheus pattern](https://prometheus.io/docs/instrumenting/writing_exporters/#failed-scrapes).

Both entry points enforce one portable export contract. They use upstream
`UnderscoreEscapingWithSuffixes` translation to check final metric and
attribute names. Reject conflicting kind or unit within a metric family,
ambiguous translated names or attribute keys, and custom names that enter
the reserved `sqlstreams_` or exporter-owned namespace. Healthy families still
export; a current-collection rejection count and diagnostic identify loss.
The warning [measurements cannot be exported](/errors/SQL0104/) names the
rejected family and reason, without payloads.
Partial rejection does not return a
collection error: periodic readers must still export the healthy families.
Reserve the two health names even against retained built-in measurements;
reserve upstream metadata names and `otel_scope_` attribute names as well.

For example, custom `billing.queue_depth` and `billing_queue_depth` both
translate to `billing_queue_depth`. Reject both families rather than choose
by row order. If one family already fails an export check, it cannot block
the other: collisions are checked only among otherwise exportable families.
Basic measurement validation stays in core constructors. This also restricts OTLP-only callers, but keeps both entry
points consistent. It does not rewrite retained measurements or enforce
metadata immutability across time.

## Derive alerts from history

Partition count, compaction read cost, worker liveness, and collector progress
use the existing alert framework. Conditions stay check-specific; shared
policy decides pending, recovery, and repeats. The
[history page](/concepts/alert-history/) covers pseudocode, timing,
diagnostic visibility, and restart/concurrency boundaries. Stream alerts check
every minute by default; collection keeps its independent 30-second interval.

## Observe collector progress independently

The collector records completion only after the whole pass succeeds. Read it
through `System().Metrics().CollectorCompletedTimestamp()`. The attribute-free
`sqlstreams.metrics.collector.completed_timestamp` gauge stores Unix seconds with
unit `s`. `System().Alerts().MetricCollectorProgress()` selects the alert.

Completion follows all collection reads and writes, including concurrent stream
work. Startup and partial passes do not refresh it. Rank-zero compaction and
stored `CreatedAt` retain the [storage-time contract](/decisions/0690/).

`worker_instance_log` rows copy instance snapshots after claim
creation and renewal, in the same datastore transaction. The log retains
instance identity, original creation time, and expiry. It adds no operation
field or calculated liveness state. Instance deletion does not delete history;
The existing manager sweep removes snapshots 24 hours after their recorded
lease expiry by default, controlled by `ManagerConfig.InstanceLogTTL`.
Log writes are part of claim and renewal success: a failed append rolls back
the instance change and returns through the existing error path.

The evaluator combines the latest collector completion with manager lease
coverage. Overlapping or touching intervals preserve pending across manager
replacement. An uncovered gap breaks the span. Retained evidence must cover
the pending window, including intervals crossing its start. Recent completion
is healthy. Otherwise, no current coverage is insufficient evidence; a shorter
coverage span is pending. Neither resolves an existing alert.

The overdue span starts at the later of current coverage start and completion
plus `MaximumAge`. With no retained completion, it starts at coverage start.
The check uses database time and the completion's Unix-second value. It reads
no separate progress observations and writes only through normal alert recording.

Graceful shutdown does not shorten a logged lease. A released or crashed
instance counts through its last recorded expiry. With the current manager
defaults, this can overstate liveness by up to 30 seconds per instance. It
proves lease coverage, not successful execution.

For example, manager instance 101 last renews at 10:00:00 with expiry 10:00:30,
then stops at 10:00:05. Replacement 102 starting at 10:00:20 preserves coverage;
starting at 10:01:00 leaves a gap. An overnight restart cannot count the stopped
hours toward pending. A short restart within the lease can preserve pending
and allow an earlier alert. This is the accepted [lease-history tradeoff](/decisions/0700/).

Collector age defaults to max(2m, 3 declared collector poll intervals), with an
explicit positive override. A running collector keeps its old rate until its
next claim. This check runs every minute and requires two unhealthy minutes;
configure it through [SystemConfig](/reference/system/#metricscollectorprogressalertconfig).
Insufficient evidence logs a warning and leaves recorded alerts unchanged.
If all checking machinery stops, SQLStreams cannot produce an outage report while
it is stopped.

## Own the export lifecycle

Configure one logical export target per installation. Multiple adapter
replicas read the same deployment totals; summing those replicas duplicates
the measurement. Provider resource identity belongs to the caller and must
identify the installation; the adapter adds no replica coordination.

Use a dedicated SQLStreams reader/provider for periodic export. A source error
skips the reader's whole collection, including application metrics attached
to that same reader. A separate application pipeline continues exporting.
The read-health 0 returned by SQLStreams does not reach a periodic exporter when
collection fails; monitor pipeline errors or missing exports there.

For example, `billing` loses Postgres while its payment handler stays healthy.
Its SQLStreams periodic reader reports the error and skips export; the separate
payment-metrics provider continues exporting. The next successful SQLStreams read
exports normally, with no cached failure to clear.

Periodic-provider shutdown cancels its active periodic collection, attempts a
final collection under the shutdown deadline, and closes its exporter even
if that collection fails. Supply a bounded shutdown context and check the error.

For the convenience Prometheus endpoint, drain the HTTP server first, call
`Exporter.Close(ctx)`, then close the caller-owned pool after all its users stop.
Close prevents new collections but does not wait for an in-flight scrape;
that scrape can finish afterward. A stopped reader can leave the HTTP endpoint
responding without SQLStreams data. Health reports source reads, not provider or
HTTP-server health. Do not mutate resolved config pointers while readers run.
